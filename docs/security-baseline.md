# Buddy security baseline and threat model

Version 1 — proposed baseline for issue [#46](https://github.com/HusseinMoukalled/Buddy/issues/46). Changes are reviewed through a PR.

## Scope and current state

Buddy is a Python/PySide6 desktop client on Windows/macOS backed by an API, relational
database, private object storage, and bounded processing workers. AI/ASR providers are
remote trust boundaries even when accessed through the backend. Locally hosted models
still process private data and receive only the permissions of their designated process.

Main currently implements the desktop shell, local preferences, and a backend health
adapter. This document defines requirements for the rest of the system, not completed
authentication, encryption, deletion, provider agreements, or production readiness.
The API foundation in [#2](https://github.com/HusseinMoukalled/Buddy/issues/2) must remain free of private domain endpoints until their own
authentication/authorization requirements are implemented.

Assets: account/session credentials; original PPTX and notes; rendered slides; extracted
text/shape geometry; semantic graphs and corrections; microphone audio; transcripts;
presentation state/history; QA screenshots; prepared demo inputs/outputs; signing keys
and provider/cloud secrets. Presentation material and speech are private by default.

Additional local boundaries are GUI ↔ background thread/process; application ↔ cache
directory; application ↔ OS credential store; presenter controls ↔ audience surface; and
Buddy-owned renderer ↔ any installed PowerPoint or external demo application. Workers
must not inherit more permissions or secrets than their task needs. GUI state mutates
only on the Qt GUI thread; cancelling a task also invalidates its future results.

## Required controls

| S01 | Use the selected identity service's supported desktop session flow; expire/revoke sessions. Store persistent tokens in the OS credential store. Do not ship backend/provider secrets or put tokens in URLs/logs. On credential-store failure, require sign-in rather than writing plaintext. | [#5](https://github.com/HusseinMoukalled/Buddy/issues/5), [#26](https://github.com/HusseinMoukalled/Buddy/issues/26) | Recovery, expiry, restart, sign-out and credential-store failure tests |
| S02 | Check ownership/role server-side for every deck, analysis, asset, job, correction and session operation/event subscription. Deny unknown/cross-account resources. | S04 | Source and derived objects are private. | S07 | Capture audio only after an explicitly started session and required OS/device permission. | S08 | AI proposes one typed allowed action or no action. Deterministic policy enforces confidence, freshness, state version, cooldown and manual priority. | S09 | Authenticate the session transport; validate schemas and actor/event permissions. | S13 | Bound upload/job concurrency, session/event/audio usage, provider deadlines and spend with configurable quotas and rate limits. Measure overload and fail recoverably. | S15 | Audit security-relevant account/deck/session changes and administrative actions using actor/resource/action/outcome/request ID. Never log credentials, raw audio, full transcripts, private slide bodies or sensitive filenames. Protect audit access and define retention. Alerts and runbooks cover exposure, provider/worker failures and suspicious access. | [#26](https://github.com/HusseinMoukalled/Buddy/issues/26), [#39](https://github.com/HusseinMoukalled/Buddy/issues/39), [#35](https://github.com/HusseinMoukalled/Buddy/issues/35), [#36](https://github.com/HusseinMoukalled/Buddy/issues/36) | Redaction fixtures, bounded metrics and incident runbook/retention review |

## Windows/macOS and capability boundaries

The GUI, background tasks and OS adapters have separate contracts. Device/process/window
operations use bounded adapters with cancellation and permission/device failure results;
they must not block the GUI thread or blindly retry revoked permissions.

| Capability | Minimum boundary and behavior | Owners |
| --- | --- | --- |
| Microphone | Windows respects OS/app/device access settings; macOS uses required usage declarations and permission flow. No capture permission during library browsing. Denial/revocation/device removal stops capture and exposes recovery. | [#15](https://github.com/HusseinMoukalled/Buddy/issues/15), [#28](https://github.com/HusseinMoukalled/Buddy/issues/28), [#42](https://github.com/HusseinMoukalled/Buddy/issues/42) |
| Screen/viewport capture | Prefer the Buddy-owned rendering surface. If native OS capture is necessary, request only permissions needed for the audience/test window, disclose capture and honor revocation. Never capture the whole desktop as a fallback. | [#48](https://github.com/HusseinMoukalled/Buddy/issues/48), [#50](https://github.com/HusseinMoukalled/Buddy/issues/50), [#28](https://github.com/HusseinMoukalled/Buddy/issues/28) |
| App/terminal control | No unrestricted automation privilege in the AI runtime. Windows and macOS adapters constrain target processes/windows and prepared actions. macOS automation/accessibility permissions, where needed, must be explicit and revocable; no bypass of OS protections. | [#20](https://github.com/HusseinMoukalled/Buddy/issues/20), [#26](https://github.com/HusseinMoukalled/Buddy/issues/26), [#28](https://github.com/HusseinMoukalled/Buddy/issues/28); dedicated demo issue |
| PowerPoint | Buddy's Qt image player is distinct from controlling installed PowerPoint. Native PowerPoint integration requires its own supported API, OS adapter, fidelity/security boundary and permission review. It is not supplied by PySide6/python-pptx. | [#10](https://github.com/HusseinMoukalled/Buddy/issues/10), [#13](https://github.com/HusseinMoukalled/Buddy/issues/13), [#28](https://github.com/HusseinMoukalled/Buddy/issues/28); feature-specific issue before native control |
| Distribution | Least-privilege packaged app; supported OS/architecture matrix; Windows signing and macOS signing/notarization handled in protected release environments. Runtime requests only enabled feature permissions. | [#28](https://github.com/HusseinMoukalled/Buddy/issues/28), [#38](https://github.com/HusseinMoukalled/Buddy/issues/38) |

## Review and maintenance

Before the first production deployment ([#27](https://github.com/HusseinMoukalled/Buddy/issues/27)/[#38](https://github.com/HusseinMoukalled/Buddy/issues/38)), the team reviews this baseline, the
implemented control evidence and every unresolved high-risk decision. Production
